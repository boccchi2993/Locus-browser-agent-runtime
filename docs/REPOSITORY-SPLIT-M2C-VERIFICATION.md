### 8.1 F1 — the optional-capability decision is now really wired to the task path

The review confirmed: `imageInputGateAvailable()` read the RUNTIME declaration for a HARNESS capability (the runtime declares no `capabilities` section, so the guard silently returned "available" and never fired); `prepareTask` discarded the `checkCoreCompatibility` result; `capabilityComposition:false` still built a full task environment (the null-manager guard is a different concept from a declaration-driven disable); CC6 only proved the checker lists missing optionals, never that the Product acts on them.

Landed (store + requirements table):

- **One frozen per-task decision.** The gate at `prepareTask` step (0) keeps the frozen `checkCoreCompatibility` result as THIS task's decision (`taskCompatibilityDecision`, `Object.freeze`): `imageInputGate` / `capabilityComposition` / `nativeToolCalls` booleans plus the raw check. Every later consumer reads that object — no later async phase re-reads a declaration that may have changed, and there is no page-level mutable "current compatibility state". A declaration change mid-task cannot rebind an adopted decision; the next task re-checks (OPT-D).
- **Harness declaration seam.** `harnessDeclaration()` mirrors the runtime side: the `hooks.harnessCapabilities` seam may host a genuinely different-declaring harness generation; production resolves the REAL public entry. The seam substitutes the DECLARATION only — the same `checkCoreCompatibility` always runs (no skip mode), and an injected declaration is checked exactly like a real one.
- **imageInputGate missing** → text-only degrade through the explicit warning: zero attachment reads, zero ingest, zero capability probe, zero image send; the user's uploaded files are kept; no approval ask. The previous wrong-core read is gone (OPT-A proves the degrade with a fully live image path — real `AttachmentStore`, real persistence, a readable PNG — so it cannot be the store-unavailable fallback; the same stores send the image on the next task once the real declaration is back).
- **capabilityComposition missing** → zero capability work on the task: no `refreshSkillPresence`, no `buildTaskEnvironment`, no plugin payload generation (the runtime returns to core-only), no skill mounts (OPT-B, counted on the real manager). With any USER-ENABLED capability present, the task is REFUSED explicitly (`capability_composition_unavailable`, naming the enabled ids) at the gate, before every side effect — silently ignoring user-enabled items is not a safe degrade (OPT-C: zero model / prepare / execute / tool / required-write).
- **Requirement-table rules rewritten to the implemented behavior** (the old `capabilityComposition` rule — "existing null-manager product guards" — described a different mechanism than the declaration rule it claimed to implement).
- **nativeToolCalls stays optional with real evidence**: OPT-E drives a strict text-fallback round trip (fenced-JSON tool call, `<tool_result>` feedback) through the real entry with `nativeToolCalls:false` declared — the rule's substance, actually executed. `executionKinds.python` stays optional: OPT-F completes a real shell task on a shell-only runtime declaration. Neither rule needed reclassification to required: both degradations are real and now demonstrated. Had one not been supportable, the review's alternative (declare it required and reject early) was available and is the documented policy for future rules.

Failure-first evidence: with the pre-fix `store.js` restored, the new suite fails loudly — I6.port-version 3 FAILs (the seam/checker did not exist) and OPT-A never completes (the old guard read the wrong core, so the task SUSPENDED on an image-capability ask the contract says must never happen; Node exits non-zero with the unsettled submit). Same suite against the fix: 87/87 PASS.

### 8.3 F3 — the python-authority sequential-run first failure: root cause NOT confirmed (evidence correction)

The original record attributed the failure to "sequential-run load-type flake … not a regression", citing the M0-baseline occurrence, an unchanged worker diff, and the standalone re-run. The review correctly rejects that: those three facts do not establish a same root cause and do not exclude a regression. Correction with the preserved evidence (`/tmp/m2c-evidence/e2e-full.log` and `python-authority-standalone.log`, out of tree — the quotes below are their content):

- **What failed.** `npm run test:e2e` (single sequential orchestrator run, 19 suites): `e2e-python-authority` 54 PASS / 2 FAIL — `E3 js.fetch attempt denied at the policy layer` and `E3c isPythonNetworkDenied separates the denial from every unrelated result shape`. The suite's single re-observe fired ("# E3 attempt failed without presenting the denial; re-observing once") and BOTH attempts failed identically. E3c's check contains one non-constant term — `isPythonNetworkDenied(e3)` — so its failure adds no independent information beyond E3's.
- **Preserved result shape.** E3's check detail keeps the output head and tail: a Python traceback through `_pyodide/_base.py` `eval_code_async` ending `File "<exec>", line 2, in <module>` + `SystemError: error return without exception set` — Pyodide's JS→Python exception bridging surfacing a SystemError instead of the JsException carrying the policy marker. Honesty note: the 200-char JSON truncation cuts BEFORE the `success` key of attempt 2, so attempt 2's `success` flag is NOT preserved in the log; attempt 1's `success === false` is established by the re-observe branch condition itself.
- **The denial itself held.** `E3b js.fetch produced ZERO requests` PASSED for the same attempts, and `E16 probe server received ZERO requests across the entire suite` PASSED — the network boundary was enforced in every attempt; the divergence is exception PRESENTATION only. This is the load-bearing fact separating the observed failure from any egress weakening.
- **Run conditions.** The sequential orchestrator had run ~10 prior suites (each spawning its own Chrome) before this one; `E1 cold boot took 2s` (CDN prewarmed, `{"prewarmed":true,"missing":[]}`). Later in the SAME run, after a full reset + re-bootstrap, `E11b network still denied after reset` PASSED with the marker presented normally — the same worker/bootstrap path presented the denial correctly minutes later in the same run.
- **Standalone re-run** (same commit, own Chrome): 56/56, E3 green on the FIRST attempt (no re-observe line), same 2s cold boot. This proves the suite passes under standalone conditions — nothing more.
- **The M0 precedent does NOT support "same root cause".** The M0 sequential failure of this suite was a CDP readiness timeout at app boot (BASELINE §3) — a different phase and a different failure mode; that record itself says the contention explanation "must not be cited as an established root cause".
- **No product fix exists to regress.** The F04a-era stabilization (commit `8577096`, "test: stabilize Python network denial assertion") was TEST-side only: the single re-observe plus the sharper `isPythonNetworkDenied` predicate. The exception-bridge behavior itself was never changed in product code, so "regression of a fix" does not apply; equally, the failure mode predates this branch.
- **The M2c diff touches no relevant path** (verified by `git diff 506c96f..6ab804c --stat`: no worker source, no index.html deny plumbing; shell.js gains an inert `limits` table entry). This LIMITS the plausible regression hypotheses to a pre-existing intermittent defect; it does not prove non-regression by itself.

**Disposition (corrected): root cause NOT confirmed.** Known facts: the enforcement boundary held (zero requests, twice + suite-wide); the presentation layer twice failed to rethrow the JsException and surfaced Pyodide's SystemError instead; the condition was not persistent across a re-bootstrap within the same run; standalone conditions were green. The in-suite hypothesis (bridge failure under heavy machine load, measured during F04a) remains CONSISTENT with these facts but was not isolated by experiment this round — reproducing it deterministically (a load generator against the bridge) was not performed and is the named follow-up. No assertion was modified, no retry/re-observe was added or removed, the first-failure log stays preserved out of tree. Targeted validation this round: one standalone `e2e-python-authority` run on the new head (§8.4) — a data point, not a proof.

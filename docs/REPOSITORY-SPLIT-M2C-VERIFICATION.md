- **I2 failure propagation** — `cat /missing` produces a FAILED tool result (`success:false`), the failure text reaches the next request, the real Telemetry sink records `success:false`, and the task still terminates honestly — never converted into success. Evidence: I2 block.

## 4. First failures: preserved, root-caused, fixed (no assertion loosening)

All first-failure logs kept out of tree (`/tmp/m2c-evidence/`; the failing outputs themselves are quoted here). Every fix was a real defect in the NEW code/test — no pre-existing assertion was weakened anywhere.

1. **`harnessCapabilities()` ReferenceError: `TASK_OUTCOME_REASONS is not defined`** (surfaced as `task_rejected` on a real submit in the SP8 section) — a re-export (`export { X } from './task-runner.js'`) does not bind the name in the declaring module; `harnessCapabilities()` referenced it bare. Fix: explicit `import` alongside the re-export. Evidence: store-python-lifecycle run (task_rejected event captured in the debug probe).
2. **CC1 optional-capability path bug** — `readCapabilityPath` resolved harness semantic capability names against the declaration ROOT instead of `declaration.capabilities`, so every optional capability was reported "missing" even when fully provided. Fix: harness optional paths resolve against `capabilities` (runtime's `executionKinds.python` stays a root path). Also CC1's own assertion wrongly expected a runtime `registryVersion` (the runtime host does not declare one) — test-side correction, not a code change.
3. **SP8 parked inside the wrong phase** — same root as (1); the compat gate threw, the task ended `error` before `refreshSkillPresence`. Fixed by (1); SP8 green unchanged.
4. **Joint suite, model adapter selection** — the suite first configured the `Model` singleton directly, but the store's boot `applySettings()` overwrites it from `store.settings` (default apiBase `api.deepseek.com/anthropic` → the ANTHROPIC adapter → `input_schema` wire shapes → "no visible text content" parse failure). Fix: configure the PRODUCTION settings path (`store.settings` + `applySettings()`, the wire-e2e pattern) and only attach the scripted transport to `Model.transport`.
5. **Joint suite, `productTaskVfsMounts is not defined`** — the harness self-assembly publishes `CapabilityManager`, so the store built a real manager and called the extensions.js product adapter, which the test graph had not loaded. Fix: eval the REAL `extensions.js` product half (its composition references resolve through the harness-published names — one live copy).
6. **Joint suite, eval ASI hazard** — a trailing `[a, b, c]` expression after a source ending in `}` parsed as member access. Fix: leading `;` in the eval tail.
7. **Joint suite, `vfs.read` is async** — the I1 VFS check called it synchronously. Test-side fix: awaited read.
8. **I3/I4 fake-transport fidelity** — the first parked fake ignored `init.signal`, so cancellation could not reach the in-flight request and the run body hung (Node drained the event loop). Fix: `{ park: true }` entries reject on `init.signal` abort exactly like real fetch. I3 also learned the (correct, pre-existing) product semantics the hard way: `cancelTask()` does NOT create a conversation, and `wire.calls` accumulate ACROSS tasks — test assertions moved to conversation ids + cumulative counts.
9. **I5 approval never raised** — `curl -o` on a GET is a READ-like network op by contract (NETWORK-RUNTIME: only non-read-like methods route through the execution-authorization port). Fix: the probe uses `curl -X POST` (side-effecting). Zero-dispatch oracle unchanged.
10. **I6 conversation routing for early rejection** — the compatibility gate's `blocked` exit ran BEFORE `prepareTask`'s rebind step, so the `core_incompatible` event routed into a leftover live conversation instead of the conversation the user opened. Product-side fix (store): the blocked exit binds the task's event routing to the conversation the rebind WOULD have chosen. I7's corrupt-checkpoint case additionally exposed that the replay-corrupt path is the EXISTING SILENT rejection (`restoreInto` marks `raw_invalid`; no events are emitted) — the assertion was corrected to the real contract, not loosened.
11. **store-defaults loader** — the eval-based suite needed the two new store imports inlined: the REAL `tool-adapter`/`core-compatibility` sources (not stubs) plus a `harnessCapabilities` binding (settings suites never submit tasks). CRLF note: the file has CRLF endings; line-based insertion preserved them.
12. **runtime-boundary G5 first failure** — `dist` absent in the fresh worktree (the gate compares built artifacts). Resolved by running `npm run build`; G5 green with no code change. Recorded because first-failure outputs are never silently discarded.
13. **Browser joint gate (runs 1–10, all preserved in `/tmp/m2c-evidence/joint-browser-run*.log`)** — in order: (a) a hand-written heredoc JSON literal broke JS quoting → responses are now built in the driver via `JSON.stringify`; (b) J2 readiness timed out TWICE — first misread as Pyodide download slowness (240s < the runtime's own bootstrap budget window), then diagnosed properly: every case's `submit()` must start its own conversation via the REAL `newTask()` action (a plain submit lands in the CURRENT conversation — cancel/submit never create one), so per-case title lookups never matched; (c) CDP `awaitPromise:true` made the J3 submit `evaluate` block until the task ENDED — the parked request could only settle via the model client's 180s timeout, so the task ended `error` before `cancelTask()` ever ran → J3/J4/J5 triggers are now non-awaiting; (d) two of my sed-style inserts dropped a `}` from an evaluate tail (syntax, caught by `node --check`/`wrapSafe`); (e) J5's blocked path emits no task_start backfill, so the conversation keeps the default title → id-based lookup (same lesson as I6); (f) J5's call-count assertion hardcoded 6 but J4's DENIED task legitimately makes two requests (tool call + denial continuation) → baseline-delta comparison. Final run 11: **16/16, exit 0**.

## 6. Unverified scope / honest boundary

- **Same-repo baseline only.** All evidence comes from one checkout at one commit. The three-repository clean-checkout build/test proof is M3's exit criterion and is NOT claimed here; no dependency lock tuple exists yet by design.
- **Optional-capability degradation rules are asserted at the unit/wiring level only.** The `imageInputGate`-missing rule is exercised by the checker + the store guard's logic path (CC6, wiring), not by a browser gate that removes the capability and clicks through the degraded UI; the capabilityComposition/python-kind rules are documented product rules whose absence paths reuse existing guarded behavior.
- **No interactive human pass.** The browser joint gate is a deterministic CDP driver (clicks happen inside the page through the real product actions, but no human-in-the-loop session was performed this round); screenshots were not used as evidence. The M2b interactive product-page pass (§5 of its record) is carried, unchanged by this round's diffs.
- **`hooks.runtimeCapabilities` shape is enforced only as "present and shape-checked by the checker"** — a hostile hooks declaration fails exactly like a hostile host declaration (SP11), but there is no dedicated negative test for every malformed hooks shape (the checker battery covers the shapes).
- **Contract-version bump flows** (what a future runtime `contractVersion: 2` requires of the Product) are documented in CONTRACTS §5, not exercised — only one protocol generation exists.
